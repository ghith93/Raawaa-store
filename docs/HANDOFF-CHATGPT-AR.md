منهج التطبيق في كل هجرة: **تجربة داخل `begin … rollback` على القاعدة المستضافة أولًا**،
ثم تطبيق فعلي، ثم تحقق. في `006` أُجريت ستة اختبارات سلوكية داخل معاملة متراجعة أخرى:

المشطوب، وتشغيل روتين التشطيب. **صفر صفوف متبقية**، ودالة الزناد غير مكشوفة
لـ`anon` أو `authenticated`. وفي `005`: RLS مفعّل، ثلاثة فهارس، وغير مكشوف لتلك الأدوار.

## ٤. ما نُفِّذ في الكود

- **بوابة النشر:** `deploy.yml` صار يعمل بحدث `workflow_run` بعد نجاح «Site checks»،
  لا بـ`push` بالتوازي معها. مُثبت بتشغيل نشر حقيقي نجح على `main`.
- **منع انحراف المخرجات:** `scripts/build-edge-bundles.mjs` يبني ويفحص كل الحزم
  (`outbox`, `owner`, `telegram-pairing`, `telegram-test`, `retention`)، وCI يفشل إن
  اختلفت الحزمة الملتزَمة عن ناتج البناء. أُصلح السبب الجذري لانحراف `outbox`: كان
  يستورد محرك التسعير عبر سلسلة استيرادات غير معزولة.
- **فشل التسليم لم يبقَ صامتًا:** HTTP 200 يعني أن الدفعة عملت، لا أن التسليم نجح.
  المجدول يقرأ العدّادات ويفشل عند `failed` أو `unknown`. والتنبيهات تبقى في الطابور
  ولا تُعاد تلقائيًا منعًا للتكرار.
- **التخطّي الصامت صار مرئيًا:** غياب سرّ المجدول كان يخرج بـ`0` بلا أثر، فـ«نجح» كانت
  قد تعني «لم يعمل شيء». صار يُصدر `::notice::` يسمّي السرّ الناقص.
- **الفحص المعزول:** كان يبني مخططًا صناعيًا ويطبّق `005` وحدها فيمرّ بينما السلسلة
  الحقيقية مكسورة. الآن يصطفّ `001..006` بالترتيب ويرفض أي عدد ناقص.
- **تثبيت المراجع:** كل مراجع GitHub Actions بـSHA كامل، و`playwright==1.64.1`.
- **فصل الإعدادات الداخلية:** `costing` و`apiNote` يُزالان من نسخة النشر فقط.

### خطأ وقع وأُصلح (للشفافية)

تثبيت `playwright==1.57.0` خفّض محرك WebKit نحو 11 شهرًا وأفشل اختبار التنقّل دون
اتصال عبر عامل الخدمة. الفشل تكرّر مرتين، أي لم يكن عابرًا. أُصلح بالتثبيت على
`1.64.1` — الإصدار الذي كانت CI تمرّ به قبل التثبيت — فنجح WebKit.

## ٦. ما لم يُنفَّذ — محجوب تقنيًا لا إداريًا

توكن GitHub المتاح **توكن تكامل بلا صلاحية كتابة إدارية**. كل ما يلي رُفض بـ
`403 Resource not accessible by integration` بعد محاولات فعلية:
branch protection (قراءة وكتابة)، rulesets (كتابة)، متغيرات Actions، أسرار Actions.

1. **الفحوص المطلوبة على `main`:** تُضبط من واجهة GitHub فقط.
   Settings ← Rules ← Rulesets ← `main`، وأسماء الفحوص:
   `فحص الملفات و JavaScript` · `اختبار المتصفح الوظيفي` ·
   `تدقيق الإتاحة (axe-core · WCAG 2.1 AA)` · `تدقيق أمان التبعيات المقفلة` ·
   `ESLint + html-validate` · `تحليل بنية المشروع والفحوص الأساسية`.
   ملاحظة: «اختبار المتصفح الوظيفي» يغطي Chromium وWebKit معًا.
2. **سرّ التنظيف `RAWAA_RETENTION_SCHEDULER_SECRET`:** غير موجود في Supabase، ولا
   أستطيع كتابته في GitHub. **لم أولّد سرًّا وأضعه في طرف واحد**: قيمته لا تُقرأ بعدها،
   فلن يمكن نسخها إلى الطرف الآخر. يلزم قيمة واحدة تُولّدها أنت وتضعها في المكانين
   (Supabase ← Edge Functions ← Secrets، وGitHub ← Settings ← Secrets ← Actions).
3. **مفتاحا تشغيل التنظيف:** `RAWAA_RETENTION_ENABLED=true` و
   `RAWAA_RETENTION_REVIEWED=true` في GitHub ← Settings ← Variables ← Actions.

## ٧. حالة التنظيف الدوري

جدولة `cron: '17 3 * * *'` أُضيفت وموافَق عليها من المالك، لكن **التنظيف لن يعمل**
حتى تكتمل النقاط 2 و3 أعلاه. هذا مقصود ومغلق fail-closed:

- الدالة بلا سرّ ترد `503`.
- المفتاحان يحكمان **كل** مسار، المجدول واليدوي معًا؛ إسقاط أي منهما يوقف التنظيف
  فورًا بلا تعديل كود. والتشغيل اليدوي ما زال يحتاج اختيار تأكيد، افتراضيًا `disabled`.
- اختبار يثبّت أن فرع الحدث يقع **داخل** المفتاحين لا قبلهما، حتى لا يتجاوزهما أحد.
