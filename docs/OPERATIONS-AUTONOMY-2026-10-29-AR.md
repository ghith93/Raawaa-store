# تشغيل رواء بأقل تدخل — 2026-10-29

## ما يعمل وما لا يعمل

- الموقع الثابت ورابط واتساب موجودان في المستودع. النشر الحالي يعتمد سير GitHub Actions الذي ينشر من `main` إلى Cloudflare؛ الفرع الحالي لا ينشر تلقائيًا إلى الإنتاج. آخر تشغيل سابق للمراقبة بتاريخ 29 أكتوبر 2026 كان ناجحًا في الوظائف الأربع وفق GitHub؛ هذا تقرير تاريخي لا يضمن استمرار الموقع.
- أضفنا في الفرع الحالي فحصًا يقارن رقم واتساب وكل حجم بسعره ورسوم منطقتَي التوصيل وخيار التوصيل المجاني مع `js/config.js` في نسخة الشفرة المفحوصة. الفحص القديم كان يكتفي بوجود الأرقام منفصلة، فلا يكتشف تبديل الأسعار بين الأحجام. الفحص الجديد لا يشغّل JavaScript القادم من الموقع؛ وعند تغيير صيغة الإعداد يجب تحديث المحلل واختباراته. لا يفحص جميع بيانات الدفع، ولا يتحقق من تفعيل رقم واتساب أو وصول الرسائل. المصدر المرجعي هو النسخة المفحوصة من الفرع، لذلك يشتغل الإنتاج المجدول على النسخة الافتراضية، وأي تشغيل يدوي على فرع غير منشور قد ينتج إنذار اختلاف صحيحًا لهذا الفرع.
- تغييرات هذا الفرع لا تُفعّل مراقبة الإنتاج المجدولة حتى تصبح في الفرع الافتراضي. [GitHub يوضح](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) أن التشغيل المجدول قد يتأخر أو يُسقط وأنه قد يتعطل بعد 60 يومًا من عدم النشاط في المستودعات العامة. فشل المهمة لا يعني أن الوكيل حاضر أو أنه سيصل تنبيه إلى المالك؛ التنبيهات تعتمد إعدادات GitHub وصاحب الجدولة. يلزم التحقق من قناة إشعار فعلية ومراجعة دورية؛ ليس هذا ضمان مراقبة 24/7.
- مساحة العمل هنا لا تستطيع الاتصال بالموقع الحي مباشرة بسبب قيود شبكة البيئة، ولا تنزيل متصفحات Playwright من CDN. لذلك نتيجة مراقبة GitHub السابقة ليست اختبارًا جديدًا لهذه التعديلات.

## الوصول الدائم وحدوده

الوكيل يستطيع تعديل الملفات وتشغيل فحوص وعمليات GitHub المتاحة أثناء الجلسة؛ لا يمكنه منح نفسه تشغيلًا دائمًا في الخلفية أو صلاحيات لحسابات لم تُربط، ولا يضمن توفر جلسة أو خدمة مجانية إلى الأبد. الأتمتة الفعلية تكون في أنظمة مملوكة للمشروع، بأذونات محدودة وإمكانية إيقافها واسترجاعها؛ لا تُخزّن كلمات المرور أو رموز الدخول في المستودع.

Drive وNotion وSupabase موصولة بالمحادثة، لكن لم يُتحقق هنا من إعداد حساباتها أو صلاحيات موارد معينة. لم يُربط WhatsApp أو Meta أو حساب Cloudflare مباشرة بالمحادثة. لا نغيّر إعدادات حسابات عشوائية، ولا ننشئ بيانات عملاء أو أسرارًا لمجرد امتلاك الصلاحية. تأكيد مكونات المنتج وسياسة الاستبدال والتوصيل والدفع والتوفر وتنفيذ الشحن يحتاج صاحب المشروع أو مزودًا فعليًا.

## أبحاث تكميلية قبل أي أتمتة محادثات

- [تسعير Meta الرسمي](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing): الرسائل عبر منصة WhatsApp قد تكون مدفوعة حسب الفئة والسوق؛ تفاصيل الحصة والشروط قابلة للتغيير. لا نفعّل أي تكامل API أو حساب فوترة قبل التحقق من تكلفة السوق الفعلية.
- [ربط تطبيق WhatsApp Business بـ Cloud API](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users/) قد يفصل الأجهزة المرتبطة ويغير ميزات التطبيق؛ لا ننقل الرقم أو نعدل الحساب دون خطة ونسخ احتياطي وتحقق من أثر النقل.
- [Cloudflare Web Analytics](https://developers.cloudflare.com/web-analytics/get-started/) خيار مجاني لقياس زيارات وأداء حقيقي بعد إعداده، لكنه لا يثبت وصول طلب واتساب أو البيع ولا يغني عن مراجعة الخصوصية وCSP قبل التفعيل. لم يُفعّل في هذه الجولة.

## أولويات لاحقة

1. اختبار التغييرات عبر CI في الفرع، ثم اعتماد نشرها بطريقة GitHub المعتادة والتحقق من المراقبة الحية والتنبيه بعد الدمج؛ لا ندّعي حصول ذلك مسبقًا.
2. تقييم وسيلة تنبيه مجانية وعملية يملكها صاحب المشروع مع اختبار وصول حقيقي وعدم تسريب أرقام أو بيانات زبائن في السجلات.
3. لتقليل عمل المالك إلى الاستلام والشحن نحتاج لاحقًا تكامل استقبال فعلي ومصرح به، وقواعد تأكيد المخزون والتوصيل والسياسات، ومراقبة بشرية للإخفاقات؛ الوعد بأتمتة كل المحادثات دون هذه المتطلبات غير واقعي.
