# Runbook اختبار staging المعزول — الطلب والموافقة والانسحاب

> إصدار محلي فقط — لا ينفّذ أوامر Supabase أو يرسل رسائل. استخدم بيانات اصطناعية صريحة؛ لا تستخدم بيانات عميلات. الاختبار لا يبدأ حتى يتوفر هدف قاعدة بيانات منفصل يمكن استهدافه دون مخاطبة مشروع `Ghaioooth-core` الأساسي.

## حالة البدء الحالية

- مخطط Supabase الأساسي في `eu-west-1` لديه 16 migration، وآخرها `20261030134505/rawaa_order_retention`؛ `005_marketing_preference_events.sql` غير مطبقة.
- الهدف الأساسي لا يحتوي جدول/دالة أحداث التسويق ولا edge endpoint intake. لا توجد قيمة سر `RAWAA_MARKETING_HMAC_KEY` مهيأة.
- محاولة الفرع الأول أعادت سجلًا `is_default=true` و`with_data=false`؛ لا تستخدمه للاختبار. محاولة فرع غير افتراضي رُفضت بمتطلب Pro. لا تكرر محاولة branching أو تنشئ مشروعًا بديلًا لتجاوز القيد.
- `rawaa-outbox` وجدولة GitHub نشطان على المشروع الأساسي. لا تكتب اختبارًا إلى قاعدة متصلة بهذا outbox؛ قد يؤدي صف واحد إلى تنبيه Telegram حقيقي.
- ملف `.github/workflows/retention-scheduler.yml` محلي فقط، ومغلق افتراضيًا بمتغيري GitHub `RAWAA_RETENTION_ENABLED` و`RAWAA_RETENTION_REVIEWED`؛ الإطلاق اليدوي يتطلب اختيار تأكيد غير افتراضي. تعتمد البوابة على سياقي `vars` و`inputs` الموثقين لاستخدامات GitHub Actions في شروط الوظائف والتشغيل اليدوي ([مرجع GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)). أبقِ المتغيرين غير مضبوطين حتى اعتماد السياسة، ونجاح E2E على هدف معزول، والتحقق من migration والـendpoint. وجود الملف لا يعني أن الجدولة مفعّلة، والمتغيرات ليست بديلًا عن مراجعة الصلاحيات.
- مسار الطلب المنشور غير موجود، والواجهة العامة غير موصولة. bundle محلي ومختبر فقط.
- نُفّذ مرة واحدة smoke test SQL عابر داخل `DO` واحد على القاعدة الأساسية: أنشأ عناصر migration المرشحة واختبر DDL/RLS/المنح/التنظيف ثم أسقطها قبل اكتمال المعاملة. تحقق بعده أن الجدول والدالة غير موجودين، وأن orders/outbox بقيت صفرًا والسجل لم يتغير. هذا ليس E2E ولا إذنًا بتكرار DDL على القاعدة الأساسية؛ الاختبار الكامل ما زال يتطلب هدفًا معزولًا.

## بوابة الوصول

استخدم فقط واحدًا من التالي بعد توافره/اعتماده:

1. مشروع staging منفصل وموجود أصلًا ضمن الخطة/الميزانية، أو
2. فرع Supabase غير افتراضي، بلا بيانات منسوخة، وله مرجع DB مستقل يمكن تأكيده عبر أدوات القراءة فقط.

قبل أي DDL، تحقق أن `project_ref`/branch ref هو الهدف المعزول فعلًا. إذا أعادت أدوات المزود المرجع الأساسي أو صنّفته افتراضيًا، **توقف** ولا تستخدم `execute_query` أو `create_migration` عليه.

## شروط السلامة قبل التشغيل

- اعتماد مراجعة الخصوصية ونسخة النص `rawaa-marketing-opt-in-v2` والمدة المقترحة (90 يومًا للأهلية؛ وسجل keyed-HMAC حتى 365 يومًا كحد أقصى). اعتماد المالك لا يغني عن مراجعة قانونية محلية لازمة.
- إعادة قراءة migration history للهدف المعزول، ثم مراجعة `migrations/005_marketing_preference_events.sql` وrollback. لا تعِد تطبيق migration 004؛ هي مطبقة في المشروع الأساسي.
- إعداد مفتاح HMAC عشوائي عالي الإنتروبيا في secret store للهدف المعزول فقط؛ لا تكتبه في Git أو سجل CI أو المحادثة. لا تنسخ مفتاح المشروع الأساسي.
- نشر endpoint الطلب وowner withdrawal على الهدف المعزول فقط، مع قاعدة بياناته ومفاتيحه. تحقق من حماية CORS والهوية وrate-limit. لا تستخدم entrypoint أو config يشير إلى URL المشروع الأساسي.
- تأكد أن GitHub outbox workflow لا يستهدف الهدف المعزول، أو أن outbox worker غير موجود/معطّل هناك. لا توقف scheduler للمشروع الأساسي لإجراء هذا الاختبار.
- احتفظ بقيم الاختبار الاصطناعية محليًا فقط، ولا تضعها في ملفات tracked. لا تستخدم رقم هاتف حقيقيًا أو وجهة Telegram حقيقية.

## سيناريوهات القبول

1. **الاختيار الافتراضي:** طلب اصطناعي بلا opt-in؛ يُحفظ الطلب ولا يُنشأ حدث marketing.
2. **الاختيار الصريح:** طلب اصطناعي جديد مع opt-in؛ يُسجّل `opt_in` بversion v2، digest HMAC فقط، وقت/مصدر، ولا يوجد رقم خام في جدول الموافقات أو الرد أو السجلات.
3. **فشل التخزين:** عند غياب المفتاح أو الجدول، يبقى الطلب محفوظًا، ويعرض الرد `not_recorded`؛ لا يصبح الرقم مؤهلًا لأي تسويق.
4. **انسحاب المالك:** سجّل withdrawal عبر هوية المالك؛ يجب أن يصبح `canReceiveManualMarketing` false قبل أي إجراء إرسال.
5. **إعادة المحاولة:** كرر الطلب بالمفتاح نفسه بعد الانسحاب؛ النتيجة `unknown` ولا يُضاف opt-in جديد ولا تنبيه ثانٍ.
6. **انتهاء الأهلية:** حدود 90 يومًا تُرفض بعد انتهاء المدة وأي timestamp مستقبلي مرفوض. لا تُرسل رسالة فعلية حتى في staging.
7. **تنظيف الدليل:** تحقق من الوظيفة bounded ببيانات مصطنعة قديمة في قاعدة الاختبار فقط؛ لا تختبرها على سجلات عميلات.
8. **التراجع والتنظيف:** احذف صفوف الاختبار ومخرجاتها من الهدف المعزول، تحقق أن العدادات عادت للصفر، ثم أوقف/احذف endpoint الاختبار إن كان مؤقتًا. لا تستخدم rollback 005 على بيئة مشتركة؛ فهو يمحو سجل الموافقات/الانسحابات.

## معيار الإيقاف

توقف فورًا إذا: لم يُثبت أن الهدف معزول، secret غير متاح، RLS أو سياق الدور غير واضح، outbox قابل للإرسال، migration history مختلفة، أو أي خطوة تتطلب تجاوز plan/permissions أو نشر endpoint على الموقع العام. سجّل السبب والمرجع فقط، ولا تنشئ صفوفًا يدويًا في قاعدة المشروع الأساسي.

## خيارات التنفيذ العملية — ترتيبًا

1. **الآن، بلا كلفة/تغيير بعيد:** اختبار migration 005 على PGlite في CI موجود وناجح (run 41197731262). يختبر SQL والقيود والمنح/RLS والتنظيف والتراجع، لكنه قاعدة PostgreSQL مضمّنة أحادية الاتصال، ولا يمثّل إعدادات Auth/API/Edge في Supabase ([مواصفات PGlite](https://github.com/electric-sql/pglite)). أبقِه فحص SQL فقط؛ لا تسمّه E2E.
2. **أفضل خطوة بلا Pro لاختبار SQL محليًا:** أُضيف الآن `npm run test:marketing:supabase-local` كمسار جاهز يستهدف Supabase CLI محليًا فقط. ينشئ إعدادًا ونسخة migration مؤقتين خارج المستودع، يطبّق bootstrap محليًا ثم المرشح 005، ويشغّل اختبارات pgTAP ثم يوقف المكدس ويحذف مجلد العمل. لا ينفّذ `supabase link` أو أي أمر بعيد، ويفشل بوضوح إذا غاب Docker أو CLI بدل تثبيت أدوات. توثيق Supabase يشرح اعتماد المكدس المحلي على CLI وDocker واختبارات pgTAP. هذا الـsandbox لا يحتوي Docker أو CLI، لذلك تحققت من حارس المتطلبات فقط ولم أزعم تشغيل Supabase local stack. الاختبار يغطي SQL/المنح وRLS والتنظيف؛ ولا يختبر Edge E2E أو Auth/PostgREST الفعليين بعد. أُبقي Telegram/WhatsApp غير مهيأين ولا أشغّل outbox worker. [دليل التشغيل المحلي](https://supabase.com/docs/guides/local-development/cli-workflows) و[مرجع CLI للاختبارات](https://supabase.com/docs/reference/cli/start).
3. **E2E على Supabase مستضاف:** استخدم هدف staging معزولًا موجودًا ومصرحًا، مع outbox معطّل/ممنوع من الإرسال، أو فرعًا مؤهلًا على الخطة. لا تكرر smoke test العابر على المشروع الأساسي ولا تُنشئ مشروعًا لمجرد الالتفاف على شرط الخطة. Branching تتطلب Pro؛ والفروع تحاسب على الاستخدام الفعلي ولا يغطيها Spend Cap، لذلك ليست حلًا مجانيًا ([رسوم branching](https://supabase.com/docs/guides/platform/manage-your-usage/branching)، [الخطط والنشر](https://supabase.com/docs/guides/deployment)).

**التوصية:** استمر باختبار PGlite الموجود؛ ثم جهّز local Supabase في بيئة Docker مناسبة قبل طلب صلاحية أو صرف على Branching. إلى أن يتوفر Docker/CLI أو هدف staging صالح، لا يوجد E2E مستضاف يمكن تنفيذه بأمان من هذا الـsandbox.

## التنفيذ المحلي البديل المتاح الآن

إلى حين توفر هدف مؤهل: شغّل `node --test order-system/*.test.mjs` و`npm run test:marketing`. أُضيف `marketing-preferences-pg-test.mjs` إلى نمط `order-system/*-pg-test.mjs` الذي يكتشفه CI الموجود، ليختبر migration 005 على قاعدة PGlite مؤقتة مع أدوار وقيود وصلاحيات وتنظيف وتراجع؛ لم أُشغّله محليًا لأن PGlite غير موجود هنا ولم أُثبّت حزمة جديدة؛ شغّله CI الموجود بنجاح في [run 41197731262](https://github.com/ghith93/Raawaa-store/actions/runs/41197731262). يصف مشروع PGlite نفسه بأنه PostgreSQL مضمّن مبني على WASM ويمكن تشغيله كقاعدة مؤقتة في الذاكرة ([المصدر، راجِع 2026-10-31](https://github.com/electric-sql/pglite))؛ لذلك هو بديل لاختبار SQL معزول، لا بديل لخدمات Supabase أو Edge E2E. كما يشغّل `order-entry-bundle-integration.test.mjs` الحزمة المولّدة داخل VM مع mocks لـPostgres وTurnstile؛ mocks لا تثبت قاعدة أو endpoint حقيقيًا.
