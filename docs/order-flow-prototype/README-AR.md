# معاينة نموذج الطلب والانسحاب

**نموذج داخلي فقط، غير منشور وغير متصل.** لا تستخدم بيانات حقيقية. النموذج يفحص الحقول في المتصفح ثم يمسحها؛ لا يرسل طلبًا ولا يحفظ موافقة أو تفاصيل.

## ما يُراجع هنا

- اختيار الحجم والكمية ومنطقة التوصيل وطريقة الدفع وخيارات العطر/الزيت تُبنى من `js/config.js`. يظهر ملخص مرجعي متجدد بحاسبة `order-system/order-pricing.js`، وتتحقق الاختبارات من تطابقه مع حساب الخادم (`order-system/order-core.mjs`) لعروض وأحجام وطرق دفع مختلفة. تُعرض المبالغ المرجعية الكسرية لأقرب دولار مع `≈`، بينما تبقى المقارنة والحسابات بالسنتات الدقيقة؛ إضافة الزيت ذات السعر غير المعتمد تُستثنى وتُعلّم بوضوح. لا يحسم الملخص التوفر أو السعر النهائي.
- موافقة معالجة الطلب مطلوبة داخل النموذج، وموافقة الرسائل التسويقية مستقلة واختيارية وغير محددة مسبقًا.
- رسالة الانسحاب تفتح مسودة WhatsApp إلى رقم المتجر من `js/config.js`؛ لا تُرسل حتى تضغط العميلة «إرسال» بنفسها.
- صياغة الموافقة والخصوصية مقترحة وليست مراجعة قانونية أو تفعيلًا لتدفق حقيقي.

## سبب تحسين ملخص السعر

مراجعة إرشادات هندسية عامة بتاريخ 2026-10-31 دفعت إلى عرض السعر والمكونات قبل أي خطوة قد تُفهم كإرسال: توصي OWASP بإعادة حساب القيم الحساسة على الخادم وعدم الثقة بإجمالي يرسله المتصفح، وتوصي مواد W3C للنماذج بإتاحة مراجعة بيانات المعاملة وإعلان التغيرات بوضوح. لذلك يستخدم النموذج حسابًا محليًا مرجعيًا، ويختبر تطابقه مع حساب الخادم؛ الخادم وحده هو المرجع عند أي ربط مستقبلي، وإضافة الزيت غير المسعّرة لا تدخل في المجموع. هذه إرشادات عامة، وليست دليلًا على زيادة التحويل أو مراجعة قانونية.

- [OWASP Business Logic Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html) — اشتقاق الأسعار والقيم الحساسة من إعداد موثوق على الخادم، ومراعاة idempotency للعمليات التي قد تتكرر.
- [W3C WAI Forms: User Notification](https://www.w3.org/WAI/tutorials/forms/notifications/) — ربط الإرشادات والأخطاء بالحقول وتقديم رد مفهوم.
- [W3C WAI Developer Modules: Forms](https://www.w3.org/WAI/curricula/developer-modules/forms/) — إتاحة مراجعة بيانات المعاملة قبل اعتمادها وإيصال حالات التغيير.

## حد مهم في الانسحاب

الرابط قناة اتصال فعلية لطلب الإلغاء، لكنه **لا يغيّر سجلًا أو قائمة استبعاد تلقائيًا**. أُضيف محليًا عقد الخدمة وAPI المالك، وadapter PostgreSQL يقبل HMAC keyed فقط، وruntime/entrypoint للانسحاب، واختبارات mocks. كذلك توجد migration 005 مرشحة محليًا فقط؛ لم تُطبق أو تُختبر على PostgreSQL. مفتاح HMAC غير مهيأ، وendpoint غير منشور، وخيار الموافقة في النموذج غير مربوط بمسار الطلب؛ لذلك لا يوجد سجل موافقات/انسحابات حي أو خدمة تسويق متصلة. مراجعة محلية تقترح أهلية تسويق 90 يومًا وحفظ سجل HMAC حتى 365 يومًا كحد أقصى؛ المدتان غير معتمدتين ولا فعالتين. لا ترسل رسائل تسويقية ولا ترفع جمهورًا. قبل التفعيل يلزم مراجعة السياسة والمدة، وإعادة فحص سجل migrations، وتطبيق المرشح بموافقة، وربط التسجيل والانسحاب بمنع فعال للإرسال، ثم اختبارًا شاملًا ببيانات اصطناعية.

## المعاينة والاختبار

يفتح رابط «نموذج الطلب» في مكتب التسويق المحلي. تستخدم الاختبارات Node المدمج فقط:

```sh
npm run test:order-preview
```

لا تفتح رابط WhatsApp أثناء الاختبار؛ يكفي فحص الرابط المركّب محليًا. لا تفعّل هذه الصفحة على الموقع العام قبل موافقة المالك ومراجعة السياسة والأمان وتكامل الخدمة واختبارها ببيانات اصطناعية.
