# خطة رواء الشاملة: الطلبات ومدير المشروع متعدد الوكلاء

**تاريخ التحديث:** 31 أكتوبر 2026. **الحالة:** خطة تنفيذية حيّة، وليست شهادة بأن المراحل التالية أُنجزت. المصدر المرجعي للأسعار `js/config.js`، وللتفويض والادعاءات `AGENTS.md`. لا تضع بيانات العملاء أو الأسرار في هذه الوثيقة أو GitHub Issues أو سجلات المستودع العام.

## الهدف والنتيجة المطلوبة

توفير متجر يستطيع العميل إرسال طلب موثوق منه، ويصل تنبيه للمالك ولوحة خاصة لتجهيزه، ثم فريق رقمي يراقب الجودة ويرتب المهام ويساعد في التطوير والمبيعات. دور المالك استلام الطلب وتجهيزه وإرساله، وقرارات التجارة أو المصروفات التي لا يمكن تفويضها بأمان. الاعتماد على خدمات مجانية متاحة للحساب، دون ترقية أو دفع تلقائي. **لا وعود بتوافر دائم أو مبيعات أعلى.** نموذج AI مساعد وليس جزءًا لازمًا لحفظ الطلب أو إرساله.

## التصميم المستهدف

1. **نظام الطلبات الحتمي**: حساب الأسعار من الخادم، تخزين ذري، outbox، محاولات مضبوطة ولوحة خاصة. لا يحتاج AI ولا GitHub Actions لحفظ الطلب.
2. **أحداث وملخصات آمنة**: حالات صحة ومقاييس مجمعة فقط، لا أسماء/هواتف/عناوين/نصوص زبائن للـLLM أو GitHub؛ تنبيهات الطلبات الخاصة إلى المالك وحده.
3. **المنسق**: مهام محددة بجدول ومحدد موارد ومعرّف تشغيل وحالة ومصدر وموعد ومحاولات وسجل ووقف. يبدأ بسيطًا، وتقارن تجربة Cloudflare Agents مع LangGraph.js قبل تثبيت أحدهما. لا تعد جلسات Arena عملية تعمل بعد انتهاء المحادثة.
4. **المستشارون**: مدير أولويات، مبيعات ومحتوى، تقنية وGraphify، مراقبة الطلبات. لا يعني تعدد الأدوار تعدد نماذج أو تشغيلًا متواصلًا؛ نبدأ بأقل عدد من استدعاءات النموذج.
5. **مراجع مستقل وسياسة خارج النموذج**: تحقق آلي من المخرجات والحقائق والصلاحيات قبل أي تأثير. أدوات محددة الغرض وصلاحياتها أقل ما يمكن؛ لا shell عام أو SQL عام أو أسرار ضمن prompt. كل المحتوى الخارجي وتعليمات العملاء والمخرجات بيانات غير موثوقة.
6. **قناة المالك**: تقرير مفيد قصير على تيليغرام، دون بيانات حساسة في GitHub، وحدود واضحة للإشعارات والتكرار. لا تمنح أوامر البوت صلاحية دون تحقق هوية وحماية إعادة تشغيل.

### M1 — إكمال الطلبات الحقيقية الآمنة (أولوية أولى؛ تمنع M6 التجاري)

- [~] عميل الطلب المرحلي يوقف انتظار الشبكة بعد 15 ثانية افتراضيًا ويعتبر النتيجة مجهولة مع إبقاء مفتاح التكرار؛ اختبار محلي يحاكي المهلة وإعادة التحميل. لا يحل ذلك فقد المفتاح عند إغلاق التبويب ولا يفعّل الطلبات أو يثبت تكامل الإنتاج.

- [~] التحقق المرحلي للهاتف يشترط ٧ أرقام فعلية على الأقل ويقبل الأرقام العربية والتنسيقات الشائعة، لكنه لا يثبت قابلية الرقم للاتصال. وافق المالك سابقًا على حد أقصى 365 يومًا لتنقيح بيانات الطلب بعد الإغلاق؛ هذا لا يمنح موافقة تسويق. وظيفة التنقيح مطبقة في staging لكن المجدول غير منشور. محليًا أُضيف adapter PostgreSQL keyed-HMAC، مخزن/خدمة موافقات، owner withdrawal API وruntime، وربط مصدر order API بخيار opt-in صريح لا يسجل إلا مع طلب جديد. migration 005 مرشحة فقط، والسر غير موجود، وواجهة العميل الفعلية غير متصلة، ولم تنشر endpoints. مراجعة الخصوصية المحلية تقترح 90 يومًا لأهلية التسويق و365 يومًا كحد أقصى لسجل HMAC؛ ليست مشورة قانونية أو سياسة معتمدة. خضع مصدر الطلب لاختبارات mocks، وبُني bundle محليًا، لكن لا يوجد endpoint استقبال طلبات منشور، لذا لا يمكن إجراء staging E2E الآن. قبل التشغيل: اعتماد النص والمدة، إعادة فحص migration history، تطبيق 005 بإذن، تهيئة السر، توصيل الواجهات، ونشر مسار suppression واختباره ببيانات اصطناعية. لا رسائل أو جماهير إعلانية. الأسعار والأحجام تبقى من `js/config.js`.
- [~] هوية عميل موثوقة حسب منصة النشر: أُعدّ `order-system/client-identity.mjs` (رأس منصة مكتوب فوق رؤوس العميل، رفض سلاسل XFF/Forwarded، تحقق صارم وتوحيد إملاء IPv6 وتجميع /64 اختياري، فشل مغلق) مع 18 حالة اختبار و74/0 وحدة و9/9 PGlite؛ وحماية NAT محدودة بحدود قابلة للضبط مع توثيق CGNAT. روجعت قواعد الوصول والتنظيف وقابلية التراجع لترحيل محدد المعدل `003` **وطُبّق مرة واحدة** يوم 30 أكتوبر (`rawaa_order_rate_limit`، مُتحقق من RLS والصلاحيات والفهرس). بثبة التزوير الحيّة جاهزة كأزرار في صفحة إعداد الآيفون. **رُبط المحوّل في وصل الاستقبال** `edge/order-entry.mjs` مع تضمين إعدادات المتجر من `js/config.js` وقت البناء وبصمة تحذّر من الحزمة القديمة (مُختبر سلبًا). تأكدت البثبة الحية من رأس الهوية: إرسال `8.8.8.8` كـ`CF-Connecting-IP` رُفض بـHTTP 403، و`X-Forwarded-For` أُعيد بناؤه، و`X-Real-IP` غائب، بينما `True-Client-IP` قابل للتزوير ولا يُستخدم. أنشأ المالك `RAWAA_RATE_LIMIT_HMAC_KEY` في أسرار Supabase؛ بقي إكمال قائمة M1 (تحديث إشعار الخصوصية، تنفيذ واختبار حد الاحتفاظ الذي أقره المالك، واجهة الطلب وموافقتها التسويقية المنفصلة، والاختبارات الشاملة ببيانات وهمية) قبل نشر الاستقبال وجدولة تنظيف المحدد. لا تعِد تطبيق الترحيلات المنشورة. التفاصيل في `order-system/README.md` و`docs/ORDER-SYSTEM-PROGRESS-AR.md`.
- [~] التحقق المرحلي يميز رفض رمز Turnstile الحقيقي عن تعطل الخدمة أو إعداد المفتاح (503 بدل اتهام العميل)، ويفشل مغلقًا في الحالتين؛ اختُبر محليًا ببيانات وهمية وPGlite. لا يزال ربط المفتاح والـhostname والـwidget واختبارها الحي مطلوبًا قبل الإطلاق.
- [~] النموذج المرحلي يميز اختلاف التفاصيل عند إعادة استخدام مفتاح طلب موجود، ويسمح بتصحيحها مع الاحتفاظ بالمفتاح ودون كشف بيانات الطلب؛ اختُبر محليًا حتى قاعدة PGlite وتنبيه وهمي. لا يتيح بدء طلب جديد أثناء بقاء النتيجة مجهولة. ما زال وصل الواجهة وendpoint وقاعدة البيانات والاسترداد بعد إغلاق التبويب واختبار الإنتاج مطلوبًا، مع مسار واضح للمالك إن تعذّر تذكر التفاصيل.
- [~] نشر outbox ومُجدول موثق الهوية ومحدود: الدالة `rawaa-outbox` منشورة (batch محدودة بثلاثة عناصر، مصادقة سرّ بمقارنة ثابتة الزمن، بلا بيانات زبائن في الردود)، ومراجعة تعرّض الأسرار حُسمت بالدليل: لا pg_net ولا pg_cron على المشروع المشترك، ورُفض Supabase Cron لهذا السبب؛ المُشغّل المرحلّي GitHub Actions كل 5 دقائق (`outbox-scheduler.yml`) مع مجدول خارجي اختياري. اختبار فقد رد Telegram وعدم التكرار وإظهار «unknown» للمالك بدل الإعادة العمياء مغطى محليًا (9/9 PGlite). أُنشئ السرّ من المالك في Supabase وGitHub، وأعاد تشغيل يدوي HTTP 200. ما يزال: التحقق من وصول أول تنبيه فعلي (إن وُجدت دفعة معلّقة)، ومراقبة توقف المجدول (M2). لا يعد النظام بوصول مرة واحدة على نحو مطلق.
- [ ] معاينة تفاعلية على الهاتف، اختبار واجهة وتحميل وفشل اتصال وإعادة محاولة، والتحقق في DB حقيقية بصلاحيات آمنة وبيانات وهمية؛ اختبار وصول تنبيه فعلي وعرضه في اللوحة وتطهير البيانات الوهمية.
- [ ] تشغيل تدريجي مع إيقاف سريع وبديل واتساب، مراقبة للأخطاء وعدم فقد الطلبات، وتحقق حي من أول طلب اختباري. لا تتضمن العملية دفعًا أو رسالة تجارية غير مصرّح بها.
- **قبول:** طلب اختباري واحد يُحفظ ويُعرض ويصل تنبيهه، سيناريوهات التكرار/فقد الرد/التحدي/الصلاحيات ناجحة، لا تتسرب بيانات العملاء؛ قرار الإطلاق مع أدلة وخطة رجوع. الاختبار الوهمي وحده لا يكفي.
