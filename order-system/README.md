# Order system — work in progress

Not connected to the store and not suitable for real orders yet. The owner edge function is deployed for staging. Never put credentials or customer records in this directory. All tests use synthetic data. The SQL migration was applied to a private staging schema in Ghaioooth-core (20261029220654); tables are empty and are not exposed by the REST schema configuration. Do not apply it again there. Production use still requires review of retention, security, access model, failure handling and pricing.

Run the zero-dependency unit tests:

```sh
node --test order-system/*.test.mjs
```

To run the local, ephemeral PostgreSQL integration checks, install the pinned test-only PGlite outside the tracked tree and point to its module:

```sh
npm install --prefix .cache/rawaa-pgtest --ignore-scripts --no-audit --no-fund @electric-sql/pglite@0.3.14
PGLITE_MODULE="$PWD/.cache/rawaa-pgtest/node_modules/@electric-sql/pglite/dist/index.js" node order-system/schema-pg-test.mjs
PGLITE_MODULE="$PWD/.cache/rawaa-pgtest/node_modules/@electric-sql/pglite/dist/index.js" node order-system/repository-pg-test.mjs
```

These tests emulate roles and a local PostgreSQL database; they do not verify a real Supabase project's settings, network, permissions, concurrency, production credentials, Telegram, or notification delivery. The integration scripts are also configured for CI; CI results are not available until the workflow runs.

The persistence adapter requires a trusted server-side database driver and read-committed transactions. The owner dashboard and owner-only API are deployed for staging; the owner reports successful sign-in. An authenticated real order display has not been tested. Local browser tests used synthetic network responses; no iPhone browser test was performed. The customer order endpoint and outbox scheduler are not deployed.

The staged `order-http.mjs` requires explicit consent, bounded requests, a server-verified challenge and an injected distributed rate limiter; a PostgreSQL rate limiter has been prototyped locally, but no trusted client identity adapter or cleanup scheduler is configured. The owner provided a public Turnstile sitekey and saved a secret in Supabase; no live widget, verification test, or public endpoint is enabled. A failed save response is deliberately treated as uncertain; re-use the same idempotency key with a fresh challenge token. The scheduler is still required to process a saved pending outbox row after a lost response.

`telegram-pairing.mjs` is deployed as an owner-only staging function with private storage and an owner UI. The owner confirmed pairing and receipt of a live test message, and a stored recipient and consumed challenge were independently verified. No actual order alert has been tested. The owner-only test endpoint and button are deployed; the owner confirmed receiving its test message. Never use the first incoming message as proof of ownership.

`postgres-rate-limiter.mjs` is local-only. It stores HMAC identities, caps requests atomically, and needs a strong independent secret, a trustworthy canonical client identity from the deployment platform, and scheduled cleanup. Never trust arbitrary X-Forwarded-For headers. The 10-attempt/15-minute prototype also requires tuning for shared networks before launch; `limits` (attemptsMax 1–100, windowMinutes 1–1440) is now configurable at creation while the defaults stay 10/15.

`client-identity.mjs` is the staged deployment-platform identity adapter required by the rate limiter and `edge-order-runtime.mjs`. Platform-header mode reads exactly one platform-overwritten header (e.g. `cf-connecting-ip`) and refuses client-started chain headers (X-Forwarded-For, Forwarded); xff-trusted-hop mode takes only the entry appended by our trusted proxy and ignores client-forged entries in front. Values are strictly validated (no hostnames, ports, brackets, zones, or ambiguous leading zeros), IPv6 is canonicalised to one spelling per key, IPv4-mapped IPv6 keys as its IPv4 address, and `ipv6GroupBits` (e.g. 64) can group one household prefix into one bucket. Anything missing, malformed, or chained throws UNTRUSTED_IDENTITY and the request fails closed. CGNAT still puts many customers behind one IPv4 address; the adapter cannot tell them apart, so keep the limit moderate, tune `limits` for shared networks, and watch 429 rates. A live spoofing probe on the deployment is required before trusting the configuration; gateway behaviour is not always documented and has changed before. The temporary static page `https://raawaa-store.pages.dev/setup.html` generates the scheduler secret locally in the owner's browser (crypto.getRandomValues — never transmitted), links to the Supabase/GitHub secret pages, and runs the spoofing probe from Safari. Its probe endpoint is the temporary Supabase Edge Function `rawaa-header-probe` (source: `edge/owner-setup-page.mjs`), which permits only the setup site's CORS origin and implements the required POST preflight. Delete the temporary page/function after the header verification is complete.

Migration `003_order_rate_limit.sql` was reviewed 2026-10-30 (access rules: RLS on, service_role only; bounded cleanup with its expiry index; reversibility via `003_order_rate_limit.down.sql`, which drops the table and index only) and applied ONCE the same day to Ghaioooth-core as `rawaa_order_rate_limit`, verified afterwards by direct catalog queries. Never re-apply it there; future changes belong in an 004. The attempts ceiling is 100 so the real cap stays tunable in the limiter (defaults stay 10 attempts / 15 minutes).

`outbox-batch.mjs` is a local, bounded batch runner; it does not itself schedule jobs, and is not deployed. It fails closed on an absent recipient and avoids auto-retrying unknown deliveries.

`customer-order-client.mjs` is a local prototype only. It stores only an opaque idempotency key in session storage and requires a new challenge for each retry. Requests now have a 15-second default timeout (configurable within 1–30 seconds); an abort is an uncertain outcome, not proof that saving failed. After reload, re-entering the same details reuses that key; closing the tab or clearing browser data can still lose it. The timeout relies on the fetch implementation honoring AbortSignal. A staged 409 intent mismatch reports that a key already belongs to different details, without disclosing the existing order. After that response `revise` permits re-entering the original details with the same key and a fresh challenge; it does not permit resetting an uncertain intent. The customer UI must explain reconciliation or contacting the owner if details cannot be recovered. The customer UI and those remaining recovery cases must be addressed before enabling it.

`turnstile-controller.mjs` is a local adapter tested with a mocked widget. Tokens are held only in memory, cleared on expiration, consumed once, and never logged. The server verifier distinguishes token-specific rejection (403) from unavailable or misconfigured Siteverify (503), failing closed in either case; local tests use mock responses. The actual sitekey/secret and hostname have not yet been verified together with Cloudflare.

`edge-order-runtime.mjs` composes the staged order handler, server-side validation, rate limiter and private database adapter. It deliberately refuses configuration without an injected trusted identity provider and leaves notification jobs pending for a scheduler. The composed intake entry `edge/order-entry.mjs` now wires `client-identity.mjs` (platform-header mode, `cf-connecting-ip`, IPv6 /64 grouping) into it and inlines the store config at bundle time from `js/config.js` — the single price source — through `scripts/build-order-entry.mjs`, which also generates a config hash. `order-entry-bundle.test.mjs` fails the build on embedded secrets, extra imports, or a **stale bundle** (any price change in `js/config.js` without rebuilding), and the negative case is verified. The intake is NOT deployed: the live gateway probe rejected a forged `CF-Connecting-IP` value with HTTP 403, rebuilt `X-Forwarded-For`, left `X-Real-IP` absent, and showed `True-Client-IP` is spoofable; only `cf-connecting-ip` is selected. The owner has now provisioned a separate `RAWAA_RATE_LIMIT_HMAC_KEY` in Supabase (the value is never read into this repository or chat). The intake remains undeployed until the M1 gradual-rollout checklist, privacy/data-retention review, and end-to-end tests with synthetic orders are complete. The handler continues to fail closed (503) until deployed with its environment.

`edge-outbox-runtime.mjs` and `outbox-scheduler-api.mjs` are composed and deployed as the Supabase Edge function `rawaa-outbox` (verify_jwt off; its own constant-time Bearer gate replaces JWT because the caller is a machine scheduler). A dedicated high-entropy secret (`RAWAA_OUTBOX_SCHEDULER_SECRET`) gates bounded batch processing; the owner has created it in Supabase and GitHub secrets, and a manual GitHub Actions run returned HTTP 200 from the function. The workflow still skips safely if the GitHub secret is absent. `.github/workflows/outbox-scheduler.yml` is a staging trigger (every 5 minutes plus manual dispatch) that skips silently without the secret; GitHub schedules can be disabled after 60 idle days on public repos, so this is NOT a delivery guarantee — alerts stay durable in the outbox until any later run, and a second trigger (e.g. cron-job.org) can be added with the same URL and secret. Supabase Cron was rejected for now: pg_cron/pg_net are not installed on the shared project, and pg_net queues can temporarily expose request headers (and therefore the scheduler secret) to database login roles. `edge/outbox-entry.mjs` is the source entrypoint; `edge/outbox-bundle.mjs` is the esbuild bundle that is actually deployed, and `outbox-bundle.test.mjs` fails the build if the bundle gains embedded secrets or extra imports.

`customer-checkout-flow.mjs` is a staged orchestration layer: it requires consent and a fresh challenge for each attempt, and never masks a confirmed save if a widget reset fails. It is not wired to a customer UI.

`end-to-end-pg-test.mjs` exercises mocked challenge, lost confirmation, reload/retry, a bounded outbox run, mock Telegram, and an owner-authorized view on ephemeral PostgreSQL. This is not a live integration test.

For a local, AST-only architecture scan using Graphify, see `docs/GRAPHIFY-AR.md`. The graph is not a substitute for runtime verification.

The retry design was compared against [Stripe’s general idempotency guidance](https://docs.stripe.com/error-low-level): preserve the key and reconcile an unknown prior attempt before starting a new one. This is a design reference, not evidence of a Stripe integration. Siteverify tokens remain single-use according to [Cloudflare](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

The staged server checks that phone input contains at least seven ASCII or Arabic-Indic digits, with one optional leading plus and common formatting; it does not prove a number exists or is reachable. Any customer UI must describe and match the tested rules before launch. See [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/tel) and [OWASP input validation](https://top10proactive.owasp.org/the-top-10/c3-validate-input-and-handle-exceptions/).
